# 载入顺序

1. 先判断复杂度（L0/L1/L2），不要所有改动都上设计卡。
2. L2 必须先写设计卡（模板见下），落成文字后再动手。
3. 需要第二意见时，用隔离上下文的 agent 做独立评审（五项挑战）。
4. 实现遵循最小必要变更：不改名、不重构、不格式化。
5. 验证按确定性清单执行，结论必须带证据。

# 复杂度路由

| 级别 | 条件 | 动作 |
|---|---|---|
| L0 | 常量/文案/配置值，单文件，无行为变化 | 直接改 + 编译 |
| L1 | 单模块逻辑，可回滚，不涉及持久化/协议 | 3 行方案 + 改 + 单测 |
| L2 | 持久化 / 协议 / 并发 / 掉电恢复 / 功耗实时性 / 跨模块接口 | 设计卡 + 独立评审 + 验证计划 |

判定问句（命中即升一级）：
1. 改坏会丢数据或变砖吗？
2. 影响上电/掉电/复位后的行为吗？
3. 改变对外协议或文件格式吗？
4. 引入新的并发路径吗？
5. 影响功耗/时延/内存关键指标吗？
6. 失败能否回滚？

# 设计卡模板

```markdown
目标：一句话，可判定
约束：协议/时序/功耗/内存/兼容/进度
现状：文件:行 + 当前行为
候选：A 做法/代价/失败模式；B 做法/代价/失败模式
取舍：选 X 放弃 Y，理由 Z
验证：怎么证明有效 + 失败判据
影响面：调用方、影响模块、回滚路径
```

# 独立评审（隔离上下文）

只给：需求 + 关键代码（≤200 行，带 file:line）+ 方案 + 五个问题：

1. 依赖但没写出的隐藏假设？
2. 漏掉的约束（掉电/并发/兼容/回滚）？
3. 最可能死在哪一步？
4. 反方案及适用条件？
5. 裁决：通过/有条件通过/重做，只列阻塞项。

输出格式：`文件:行 | 阻塞/建议 | 触发条件 | 依据`

# 实现规则

- 最小必要变更；复用优先，禁止平行实现；
- 一次只做一件事；发现更优方案先记录，不顺手改；
- 涉及持久化/协议：先定格式与兼容策略，再写代码。

# 验证清单（按需）

1. 编译通过 + 警告清零；
2. 单测 / 源码结构断言；
3. 生成物与源一致（protobuf、配置表）；
4. 符号表 / 内存占用对比；
5. 故障注入（断电、满盘、超时）；
6. 硬件实测（电流、波形、时序）。

验证结论必须带：命令 + 输出摘要 + 产物路径。给不出 = 未验证。

# 提交规范

`<type>(<scope>): <一句话中文描述>`

- type：feat / fix / docs / chore / refactor / test / build / ci
- 一个提交一件事；不改写历史；
- 描述写做了什么，不写 "update"。

# 禁止事项

- 改测试让它通过（测试只读）；
- 把估算写成实测（数字必须标口径）；
- 跳过设计卡直接改 L2；
- 未验证就声称完成。
