# 01 · 复杂度路由：别让流程拖死小改动

> 核心问题：**不是所有改动都值得设计卡。** 判断错了，要么过度流程，要么裸奔。

## 三级路由

| 级别 | 判定条件 | 要做什么 | 典型耗时 |
|---|---|---|---|
| **L0** | 改常量/文案/配置值；单文件、无外部行为变化 | 直接改 + 编译 | 分钟级 |
| **L1** | 单模块内逻辑改动；可回滚；无持久化/协议影响 | 简述方案（3 行）+ 改 + 单测 | 十分钟级 |
| **L2** | 涉及以下任一：**持久化格式 / 通信协议 / 并发与中断 / 掉电与恢复 / 功耗与实时性 / 跨模块接口** | 设计卡 + 独立评审 + 验证计划 | 小时级 |

## 判定问句（按顺序问，命中即升一级）

1. 改坏了会不会**丢数据**或**变砖**？
2. 会不会影响**上电/掉电/复位**后的行为？
3. 会不会改变**对外协议或文件格式**？
4. 会不会引入**新的并发路径**（中断、线程、DMA）？
5. 会不会影响**功耗、时延、内存**的关键指标？
6. 失败时**能不能回滚**？回滚需要人工干预吗？

答"是"的题越多，越往 L2 靠。

## 常见误判

| 误判 | 后果 | 纠正 |
|---|---|---|
| 把"改一个字段"当 L0 | 字段进了持久化结构，旧数据不兼容 | 看它是否落盘/上线 |
| 把"加个日志"当 L0 | 高频日志拖慢实时任务 | 看频率与写入路径 |
| 把"改驱动参数"当 L1 | 影响功耗/稳定性，难回滚 | 参数属于运行时行为，升 L2 |
| L2 也硬套设计卡 | 小修小补被流程拖死 | 允许 L2 简化版：只写"约束 + 验证"两段 |

## 一条硬规则

> **级别由"最坏后果"决定，不由"改动行数"决定。**
> 改一行也可能丢数据；改五百行可能只是重命名。

## 例子

| 改动 | 级别 | 理由 |
|---|---|---|
| 把超时从 60 s 改成 90 s | L1 | 行为变化但可回滚，无持久化 |
| 给历史文件加一个新字段 | **L2** | 持久化格式 + 旧数据兼容 |
| 把 `fs_sync` 从每次写改成批量 | **L2** | 掉电语义 + 实时性 + 数据完整性 |
| 修一个拼写错误 | L0 | 无行为变化 |
| 换一个传感器驱动 | **L2** | 时序/功耗/异常路径全变 |
