# 05 · 脱机验证与模拟后端

> 判断一个固件项目的分层好不好，只看一件事：
> **业务逻辑能不能在 PC 上跑起来，并且跑的是同一份代码。**

## 一、为什么必须脱机

| 不脱机的代价 | 脱机后 |
|---|---|
| 硬件没回来 → 业务没法调 | 硬件和业务并行开发 |
| 偶发问题只能上机复现 | 用录制的数据反复回放 |
| 改一行要烧一次板 | 秒级迭代 |
| 无法做异常注入（断电、超时、满盘） | 用 mock 主动构造 |

## 二、三个层次（由易到难）

| 层 | 做法 | 能测什么 | 成本 |
|---|---|---|---|
| **L1 纯函数** | 业务逻辑抽成"输入→输出"，不碰硬件 | 算法、协议编解码、状态机 | 低 |
| **L2 接口 + mock** | 把硬件访问收进接口，写一个返回假数据的实现 | 业务流程、错误处理 | 中 |
| **L3 录制回放** | mock 读录制文件（真机日志/波形），按时间戳喂 | 真实场景复现 | 中高 |

**建议顺序**：先做 L1（改造成本最低），再对最痛的链路做 L2。

## 三、接口 + mock 的最小结构

```c
/* sensor_if.h —— 业务只依赖这个 */
typedef struct {
    int (*read)(void *ctx, float *value);
    int (*enable)(void *ctx, bool on);
} sensor_ops_t;

/* 真机实现 */
const sensor_ops_t sensor_real = { .read = real_read, .enable = real_enable };

/* 测试实现：按脚本返回，可注入错误 */
const sensor_ops_t sensor_mock = { .read = mock_read, .enable = mock_enable };
```

```python
# 回放脚本（主机侧）
samples = load_csv("record.csv")
for t, value in samples:
    mock_set_value(value)          # 喂给 mock
    business_tick(t)               # 跑同一份业务代码
assert proto_frames == expected    # 比对输出
```

## 四、mock 必须能"做错"

只会返回正常值的 mock 测不出问题。至少覆盖：

| 场景 | mock 行为 |
|---|---|
| 读失败 | 返回 `-EIO` |
| 超时 | 延迟超过阈值 |
| 数据跳变 | 突然返回 0 或极值 |
| 空间不足 | 写入返回 `-ENOSPC` |
| 掉电 | 写到一半停止，重新初始化 |

**规则：一个接口配一个"能犯错"的 mock，否则等于没测。**

## 五、常见的坑

1. **mock 不忠实**：时序、并发、错误码和真机不一致 → 真机翻车；
2. **业务仍直接调 OS**：`k_sleep`/`k_work` 散落各处 → 在 PC 上编译不过（先把 OS 收进 `osal_if`）；
3. **只测正常路径**：异常路径才是 bug 高发区；
4. **mock 自己没被测**：mock 行为与规格不符，会掩盖真实问题——给 mock 也写断言。

## 六、验收标准

> 同一份业务代码，不改一行，能在 PC 上跑完"正常 + 至少 3 条异常路径"，
> 且输出与真机一致。

达到这条，分层的价值才有证据，而不只是图好看。
