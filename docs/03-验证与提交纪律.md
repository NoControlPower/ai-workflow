# 03 · 验证与提交纪律

> AI 最容易骗人的地方不是写错代码，是**让你以为已经验证过了**。

## 一、确定性验证清单（按能自动化程度排序）

| # | 验证 | 能发现什么 | 成本 |
|---|---|---|---|
| 1 | 编译通过 + 警告清零 | 语法、类型、未使用变量 | 分钟 |
| 2 | 单元测试 / 源码断言 | 逻辑回归 | 分钟 |
| 3 | 源码结构断言（脚本 grep + 正则） | "约定被悄悄改掉"（如顺序、默认值） | 分钟 |
| 4 | 产物一致性（生成文件与源一致） | protobuf/配置生成物漂移 | 分钟 |
| 5 | 符号表 / 内存占用对比 | 代码体积、RAM 峰值变化 | 分钟 |
| 6 | 故障注入（断电、满盘、超时） | 恢复路径 | 小时 |
| 7 | 硬件实测（电流、波形、时序） | 真实行为 | 小时–天 |

**规则**：前 3 项必须做；涉及持久化/协议的加第 4–6 项；涉及功耗/实时的加第 7 项。

## 二、源码结构断言（小团队最划算的防护）

没有集成测试框架时，把"已经写错过一次"的约定固化成对源码的结构断言：

```python
# 例：校验"读失败必须先返回错误，不能当成格式不匹配去清空"
src = read("storage.c")
assert src.index("if (rc < 0) return rc;") < src.index("clear_file(")
```

**优点**：零依赖、秒级、能挡住"回头又改错"；
**缺点**：只能防结构性问题，不能证明行为正确——所以它**替代不了测试**。

## 三、AI 验证的坑（必须人工确认）

| 说法 | 真相 |
|---|---|
| "我运行了测试，全部通过" | AI 可能没跑，或跑的是旧产物 |
| "编译通过" | 可能只编了一个目标 |
| "逻辑正确" | 没证明，只是看起来对 |
| "已修复" | 没复现，就谈不上修复 |

**规则**：AI 说"通过"时，要求它给出**命令 + 输出摘要 + 产物路径**，否则不算验证。

## 四、提交纪律

```
<type>(<scope>): <一句话中文描述>

type: feat / fix / docs / chore / refactor / test / build / ci
scope: 按模块或领域
```

- 一个提交只做一件事；
- 描述写"做了什么"，不写"update/修改"；
- 需要时在 body 写"为什么"；
- **不改写历史**（除非有明确理由和备份）。

## 五、什么时候必须停下来

| 情况 | 动作 |
|---|---|
| 验证做不了（没硬件/没权限） | 明确写"未验证"，不假装通过 |
| 改动超出原范围 | 拆成两个提交，或重开设计卡 |
| 发现更优方案 | 先记录，不顺手改（防止范围蔓延） |
| 时间不够 | 宁可少做，不留半成品进主线 |
