# 02 · 设计卡与独立评审

> 设计卡解决"想清楚"，独立评审解决"别人替你看漏了什么"。

## 设计卡模板（L2 必填，一页以内）

```markdown
目标：一句话，可判定
约束：协议/时序/功耗/内存/兼容/进度
现状：相关代码位置（文件:行）+ 当前行为
候选方案：
  A. 做法 → 代价 → 失败模式
  B. 做法 → 代价 → 失败模式
取舍：选 X，放弃 Y，理由是 Z
验证：怎么证明有效（测试/数据/现象），失败判据是什么
影响面：调用方、影响模块、回滚路径
```

### 每项的最低要求

| 字段 | 不合格 | 合格 |
|---|---|---|
| 目标 | "优化日志" | "把单次刷写从 192 KiB 降到 4 KiB 级，1 Hz 链路停摆 < 50 ms" |
| 约束 | "尽量不影响" | "断电最多丢最近 N 条；不得改变对外文件长度语义" |
| 候选 | 只写一个 | 至少两个，含"不做的代价" |
| 失败模式 | 不写 | "写到一半断电 / 空间不足 / 旧数据不兼容"分别怎样 |
| 验证 | "跑一下" | "构造 3 类输入，比对输出；断电注入 20 次无半写" |

## 独立评审：五个必问

给**另一个隔离上下文的 AI**（看不到你的推理过程），只给：需求 + 关键代码片段 + 你的方案 + 这五个问题。

1. 这个方案依赖但**没写出来**的隐藏假设是什么？
2. 漏掉了哪些约束（掉电 / 并发 / 兼容 / 回滚 / 功耗）？
3. 首选方案**最可能死在哪一步**？
4. 给一个**反方案**，并说明什么条件下它更好。
5. 裁决：通过 / 有条件通过 / 重做——**只列阻塞项**。

### 输出格式（强制）

```
文件:行 | 阻塞/建议 | 触发条件 | 依据
```

禁止"整体看起来没问题"这类结论；每条必须能落到代码或条件上。

## 为什么不让同一个 AI 自审

| 自审 | 独立评审 |
|---|---|
| 共享上下文，倾向维护自己的方案 | 无立场，更容易发现假设 |
| 会复述你的理由 | 会质疑你的理由 |
| 快 | 慢但值 |

**代价**：多花 10–30 分钟；**收益**：挡住"上线后才发现"的问题。

## 评审后怎么处理

1. 每条阻塞项必须**核实**（回代码看，不是照单全收）；
2. 采纳 → 改设计卡；驳回 → 写下理由（防止以后重复争论）；
3. 被驳回的意见也要记录——它是"我们评估过"的证据。

## 一个实例（脱敏）

> 方案：把整块回绕的日志文件改成"分段追加 + 双 bank"。
> 独立评审提出的阻塞项：
> 1. 段头 CRC 失败时，读路径是否回退到旧 bank（否则会读出半新半旧）；
> 2. 旧文件与新段的 offset 映射必须定义清楚，否则 APP 读到空洞；
> 3. 轮换时创建/删除文件会放大元数据提交，需确认不会抵消收益。
>
> 这三条后来都进了实现和测试用例——**这就是评审的价值：它问的问题，就是上线后会出问题的地方。**
