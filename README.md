# ai-workflow · 我怎么用 AI 写固件

> 一个嵌入式工程师的 AI 协作方法论：**流程、分工、验证、踩过的坑。**
> 不是 prompt 合集，是"怎么让 AI 产出能交付的代码，而不是看起来对的代码"。

## 一句话定位

> AI 负责"更快地做"，我负责"做对什么、怎么验证、谁担责"。

## 我的分工（最重要的一条）

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 需求拆解、约束梳理 | 我 + AI 讨论 | AI 帮我把隐含假设摊开 |
| 方案设计、取舍 | **我拍板**，AI 出候选 | 责任在交付的人 |
| 编码实现 | AI 为主，我逐行读 | 效率差 5–10 倍 |
| 独立评审 | 另一个 AI（隔离上下文） | 避免"自己审自己" |
| 验证 | **我做**，AI 给测试设计 | AI 会"假装验证"，我必须真跑 |
| 提交、对外声明 | **我** | 责任不能外包 |

## 五步流程

```
① 复杂度路由        L0 直接改 / L1 小设计 / L2 设计卡 + 独立评审
② 设计卡            目标 / 约束 / 方案取舍 / 失败模式 / 验证 / 影响面
③ 独立评审          另一个 AI 挑五项：隐藏假设 / 漏掉约束 / 最可能死在哪 / 反方案 / 裁决
④ 最小必要变更      不改名、不重构、不格式化；一次只做一件事
⑤ 确定性验证        编译 / 单测 / 源码断言 / 符号表 / 产物一致性 / 性能回归
```

## 适合谁看

- 想用 AI 写嵌入式/固件，但怕它"写错还自信"的人；
- 已经在用 AI，但产出质量不稳定的人；
- 需要向团队证明"AI 产出可以进主线"的人。

## 不适合谁看

- 想要"一句话生成整个项目"的人——这里没有魔法；
- 不愿做验证的人——本文档的前提是**你必须真跑测试**。

## 效果（只写可核验的）

- 效率：同类模块改动，AI 起草 + 我审的耗时约为手写的 1/5–1/3（个人体感，非严格测量）；
- 质量：规则化的验证清单让"改完没跑测试就提交"基本消失；
- 代价：流程本身有开销，小改动（L0）必须允许跳过设计卡，否则会被流程拖死。

## 公开边界

**原则：思路、方法、通用数字、短篇代码可以开放；能定位到产品或公司的东西不开放。**

| 开放 | 不开放 |
|---|---|
| 流程、模板、判定标准 | 公司名、产品名、客户信息 |
| 设计取舍、通用架构 | 完整工程代码、内部路径 |
| 脱敏数字与设计参数 | 协议字段、分区地址、产线参数 |
| 短篇代码（≤80 行、通用化） | 内部文档原文、日志原文 |

判断标准：这段内容能否关联到具体产品/公司？能，就改写后再发。

> 本仓库所有内容已脱敏：不含公司名、产品名、具体协议字段与硬件标识。
> 代码示例为通用结构，数字为设计参数（可复现、不指向任何产品）。
